## 1. 产品概述

### 1.1 产品定位

面向高校校区场景的电脑维修自助下单 Web 端：客户通过手机访问页面即可完成服务选择与信息提交，店主收到通知后按客户选定的渠道完成确认、排期与交付；售后环节通过手机号关联原订单，实现 7 天保修可追溯。

### 1.2 端到端主链路（一句话概括）

客户在手机端打开页面 → 首屏展示店铺介绍文案（学生维修小店 / 专治问题 / 服务方式）与「进入」按钮 → 进入主页（顶部为修机视频背景；无视频素材时降级为蓝色渐变缓慢流动的动态背景）→ 选择「清灰换硅脂」（¥80 / ¥100 两档）或「其他问题」→ 填写联系人、手机号、品牌型号等信息，并在「电话联系 / 微信联系」中选择联系偏好 → 提交订单 → 店主收到微信通知后按客户选择的渠道联系客户。客户亦可从「售后报修」入口提交报修（清灰服务享 7 天保修），凭手机号关联原订单说明问题；全站均提供官方微信二维码，供不偏好电话沟通的客户使用。

### 1.3 产品目标

| 编号 | 目标 | 说明 |
| --- | --- | --- |
| G1 | 自助下单 | 客户在页面内独立完成信息填写，减少「什么型号」「多少钱」等重复性沟通 |
| G2 | 主力业务标准化 | 清灰换硅脂明确 ¥80 / ¥100 两档差异与 7 天保修范围，对外表述统一 |
| G3 | 信息一次收齐 | 店主获取订单后即可直接联系、排期并开展服务，无需二次问询 |
| G4 | 售后有据可查 | 客户凭手机号即可关联原订单，保修期状态清晰可判 |
| G5 | 尊重客户沟通偏好 | 提供电话、微信双渠道并由客户自选，不强制客户接受电话沟通 |

### 1.4 成功衡量指标（建议）

| 指标 | 目标值 | 说明 |
| --- | --- | --- |
| 下单表单提交成功率 | ≥ 80% | 进入表单页到提交成功的转化 |
| 首屏「进入」按钮点击率 | 持续观测 | 衡量首屏文案与视觉的引导有效性 |
| 店主首次联系时效 | 营业时间内 ≤ 30 分钟 | 以通知送达至状态变更为准 |
| 订单信息完整率 | 100% | 必填字段齐全，无需回访补录 |
| 售后订单关联成功率 | 尽可能高 | 凭手机号匹配到历史订单的比例 |

## 2. 用户角色与使用场景

### 2.1 用户角色

| 角色 | 特征描述 | 主要触点 |
| --- | --- | --- |
| 客户 | 有电脑维修需求的学生群体，绝大多数通过手机访问，且多在微信内置浏览器中点开链接；主要来源为桑浦山、东海岸两个校区；相当比例客户不偏好接听电话，更倾向微信文字沟通 | 首屏欢迎页、下单表单、售后报修页、提交成功页、官方微信 |
| 店主（xiu xiu） | 负责接单、联系客户、排期、维修及售后处理 | 微信通知、官方微信、极简后台 |

### 2.2 核心用户旅程

**下单主流程**

```
客户 → 首屏欢迎页 →「进入」→ 主页 /order
                                ├─ 选择「清灰换硅脂」（¥80 / ¥100）┐
                                └─ 选择「其他问题」（待检测报价）  ├→ 填写联系信息并选择联系偏好
                                                                  └→ 提交 → 提交成功页
                                                                        └→ 店主收到微信通知
                                                                           → 按客户选择的渠道联系（电话 / 微信）
                                                                             （上门订单需排期，可能存在等待）
```

**售后流程**

```
客户 → /aftersale → 填写手机号 + 问题描述 → 提交
     → 店主收到通知 → 电话 / 微信核对原订单
     → 7 天内且属清灰相关问题：免费返修；超出保修期或其他问题：检测后报价，客户确认再维修
```

### 5.2 主页（`/order`）

主页由「顶部 Hero 背景区 + 中部下单表单 + 底部信息区」三部分组成。

#### 5.2.1 Hero 背景视觉分层与降级策略 [REQ-02 / REQ-03]

采用四层结构，自下而上定义如下：

| 图层 | 内容 | 实现要求 |
| --- | --- | --- |
| L0 | 动态简洁背景（纯 CSS 蓝色渐变缓慢流动） | 打开即有呈现、无需下载、永不空白，作为所有场景的兜底底座 |
| L1 | 修机视频（存在素材时） | `canplay` 事件后淡入（800ms）覆盖 L0；无素材、加载失败或弱网条件下保持 L0，不做额外处理 |
| L2 | 黑色半透明遮罩 | 存在视频时须叠加遮罩以保证上层文字可读；遮罩透明度取值见 UI/UX 设计文档 §7.2 |
| L3 | 文字内容（店名 / slogan / 入口按钮） | 叠加于 L1 / L2 之上，须保证任意背景状态下的文字可读性与对比度（要求见 UI/UX 设计文档 §10「无障碍与可用性」） |

> 💡 **方案说明**：相较 v1.0，静态兜底图不再是必需项——动态背景由代码绘制、零下载，「网络差导致首屏空白」的问题在方案层面已被消除。视频 `poster`（加载期间先行展示的同场景静态图）为可选项，是否采用及画面要求由 UI/UX 设计文档定义。

**视频素材规格（存在素材时适用）**

| 项 | 要求 |
| --- | --- |
| 文件 | `hero-bg.mp4`（H.264 编码；建议去除音轨以压缩体积） |
| 分辨率 | 1920×1080（16:9）横屏；移动端以 `object-fit: cover` 居中裁切 |
| 体积 | ≤ 5MB（建议码率 2–4 Mbps） |
| 播放属性 | `<video autoplay muted loop playsinline preload="auto">`，默认静音、自动循环、无控制条 |
| 功耗控制 | 页面进入后台（`visibilitychange`）时暂停播放，回到前台恢复 |

> 视频时长、画面内容、构图安全区与循环观感要求见《前端 UI/UX 设计文档》§11「素材与图标规范」；拍摄执行参考同文档附录 B「修机视频拍摄脚本」。

**降级判定逻辑（实现参考）**

```js
const v = document.querySelector('#heroVideo');
const conn = navigator.connection || {};
const slowNet = conn.saveData === true ||
                /(^|-)2g|3g/.test(conn.effectiveType || '');   // 省流模式 / 2G / 3G
const reduce  = matchMedia('(prefers-reduced-motion: reduce)').matches;

if (slowNet || reduce) {
  v.remove();                                  // 不加载视频，保持 L0 动态背景
} else {
  const timer = setTimeout(() => {             // 3 秒内未就绪即降级
    if (v.readyState < 3) v.remove();
  }, 3000);
  v.addEventListener('canplay', () => {
    clearTimeout(timer);
    v.style.opacity = 1;                       // 淡入覆盖 L0
  });
  v.play().catch(() => v.remove());            // 自动播放被拒（如 iOS 低电量模式）即降级
}
```

**素材方案（二选一，由店主决策）【待确认：视频素材交付时间】**

| 方案 | 说明 |
| --- | --- |
| Plan A：实拍修机视频 | 视觉质感最佳（拍摄脚本见 UI/UX 设计文档附录） |
| Plan B：直接使用动态简洁背景（REQ-04） | 无需拍摄与等待，加载最快，呈现 Apple 官网式的克制高级感 |

> 代码须保留切换开关 `HERO_MODE = 'video' | 'motion'`，两套方案均可独立运行、可随时切换。

#### 5.2.2 动态背景兜底要求 [REQ-04]

在无视频素材、弱网 / 省流模式、自动播放被拒或视频加载超时等场景下，页面须以纯 CSS 动态背景作为兜底视觉，实现约束如下：

| 项 | 要求 |
| --- | --- |
| 实现方式 | 纯 CSS 实现（优先），零文件下载，页面打开即有呈现 |
| 渲染性能 | 仅驱动 `transform` / `opacity`（GPU 合成），不触发重排；移动端不得引起发热或掉帧 |
| 无障碍 | 命中 `prefers-reduced-motion: reduce` 时停止动画，保留静态视觉 |
| 可配置性 | 须支持 `HERO_MODE = 'video' | 'motion'` 开关，两套方案均可独立运行并随时切换 |
| 技术选型约束 | 不采用 Lottie（需额外素材、体积大）与 Canvas（除非存在纯 CSS 无法实现的特殊效果需求） |

## 7. 业务规则

> 本章为业务规则定义，开发侧只需保证通知携带全字段（§6.1）且后台状态可对应流转。

**沟通渠道总原则**：以客户选择的渠道为准（电话 / 微信），不强制客户接受电话沟通。涉及价格确认、增项变更等敏感沟通，**优先使用微信文字确认**——文字天然留痕，可有效降低事后争议；电话沟通达成的重要结论（价格、时间），建议以微信文字复述确认一次。

### 7.1 上门服务规则 [REQ-06-1]（已确认）

1. 客户选择「上门服务」时，表单内**固定展示以下提示文案**（文案已定稿，直接使用）：

   > ⚠️ 上门需师傅排期，具体时间以沟通确认为准。
   > 费用：桑浦山校区 10 公里内不加价；超出加收 10–20 元；东海岸校区因交通不便，请电话或微信商量。
   > 上门检查后不维修，不收费。急用建议到店。

2. **范围与收费规则**：
   - 以**桑浦山校区**为起点，10 公里范围内不加价
   - 超出 10 公里，加收 **10–20 元**（具体金额由店主依据实际距离确认）
   - **东海岸校区**因交通不便，服务时间与费用单独协商
   - **V1 不在线计算距离与费用**，页面仅展示上述规则文案；**费用由店主单独沟通确认——电话或微信均可，以客户选择的渠道为准**
3. 上门地址为**选填项**：客户可先留空（部分客户不愿在网页填写住址），沟通确认阶段补充。
4. **xiu xiu 保留拒绝任何订单的权利**（超出服务范围、排期冲突、机型特殊等）。对客户的委婉表述：「如无法上门，我们会联系您说明并建议到店送修。」
5. 通知推送时，上门订单须**高亮标记并携带期望时间**（见 §6.1 模板），便于店主排期。

### 7.2 下单后沟通节点

| 节点 | 时机 | 方式 | 目的与话术要点 |
| --- | --- | --- | --- |
| 1. 接单确认 | 收到通知后 ≤30 分钟（营业时间内；非营业时间则次日 9:00 后） | **按客户偏好：电话 / 微信** | 客户选择微信时，待好友申请通过后沟通（长时间未添加则主动致电）；确认机型、故障与套餐；「其他问题」须说明**需检测后报价** |
| 2. 预约 / 排期 | 同一轮沟通内完成 | 电话 / 微信 | 到店：约定时间。**上门：核对师傅档期并明确告知可能等待；确认地址是否在服务范围内（桑浦山 10 公里内不加价，超出加收 10–20 元，东海岸另行协商）；告知上门检查未维修不收费**；敲定期望时间，急用建议改为到店；上门前 30 分钟再次确认 |
| 3. 拆机前 | 开工前，当面或文字 | 当面 / 微信 | 告知拆机风险（老机型卡扣易断等）与数据安全提醒；确认最终价格，客户同意后再操作 |
| 4. 维修中增项 | 发现新问题时 | 电话 / 微信 | **先报价、经客户同意后再施工（推荐微信文字确认）**；客户不同意则恢复原状 |
| 5. 交付 | 维修完成 | 当面 | 验机（向客户演示温度、噪音表现）、收款、**说明 7 天保修范围**、引导添加官方微信 |
| 6. 回访（可选） | 交付后 1–3 天 | 微信 | 询问使用情况，顺势收集好评 |

### 7.3 售后沟通节点

| 节点 | 时机 | 方式 | 要点 |
| --- | --- | --- | --- |
| 1. 收到报修 | 实时 | 微信通知 | 查看手机号、问题描述及是否处于 7 天保修期内 |
| 2. 核对 | 营业时间内 ≤30 分钟 | 电话 / 微信 | 通过手机号在后台查询原订单；确认是否在 7 天保修期内 |
| 3. 判断 | 沟通中 | — | **7 天内且属清灰相关问题 → 免费返修**；超出保修期 / 人为损坏 / 其他问题 → 报价，客户同意后维修 |
| 4. 处理 | 与客户约定 | 到店 / 上门 | 维修完成后请客户当场确认 |
| 5. 关单 | 处理完成 | 后台 | 状态置为「已关闭」，并备注处理结果，避免重复争议 |

### 7.4 7 天保修规则（须写入交付话术）【待确认细则】

| 项 | 规则 |
| --- | --- |
| 保障范围 | 清灰换硅脂交付后 7 天内，与清灰直接相关的问题（温度仍高、风扇异响等） |
| 不保范围 | 人为损坏、进液、摔碰、其他部件自身故障 |
| 起算日 | **交付当天**计为第 1 天 |

> 注：交付日暂以订单创建日近似；共 7 个自然日，保修截止日 = 交付日 + 6 天；该口径与 API 契约 §3.3、数据库契约 §5 I9 一致。


## 9. 非功能性需求

| 项 | 要求 |
| --- | --- |
| 移动端优先 | 以 375px 宽度为设计基准，断点 768 / 1200；桌面端居中，内容最大宽度 1200px |
| 微信兼容（重点） | 须保证微信内置浏览器（iOS WKWebView / Android X5）下功能正常：视频自动播放失败时降级为动态背景；任何情况下不得白屏 |
| 首屏性能 | 动态背景为纯 CSS，**零下载、秒级呈现**；4G 网络下 LCP ≤ 2.5s；视频异步加载、不阻塞渲染 |
| 动效性能 | 背景动画仅驱动 `transform` / `opacity`；命中 `prefers-reduced-motion` 时全部停止 |
| 表单体验 | 手机号使用 `type=tel` 以调起数字键盘；输入框字号 ≥16px、按钮热区 ≥44px（视觉细化见 UI/UX 设计文档） |
| 图片上传 | 前端压缩（长边 ≤1920、质量 0.8）；后端限制文件类型与大小；HEIC 转 jpg |
| 防刷防重 | 规则见 §5.2.4「提交行为与异常处理」 |
| 隐私保护 | 手机号仅出现在通知与后台，公开页面不得展示；底部展示一行隐私说明 |
| 部署要求 | 必须启用 HTTPS；面向国内访问的域名需完成 **ICP 备案**（微信传播场景基本为必需项）。**已确认：由开发方负责办理，店主后续提供证件资料**（身份证 / 营业执照等，按开发方要求提供）；周期约 1–2 周，**开工后须尽早启动** [REQ-16] |
| 兼容性 | 覆盖近两年 iOS Safari、Android Chrome、微信内置浏览器；不考虑 IE |
| 埋点（可选） | 首屏「进入」点击率、表单提交转化率 |
